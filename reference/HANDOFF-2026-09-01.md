## 1. WHAT WAS BUILT

### The dead man's switch — four legs

**The problem it closes.** A nightly run that CRASHED and a nightly run with
NOTHING TO SAY were the same thing on the phone: silence. The E92 pointer
fires only when a name is waiting, so an absent pointer meant *either*
"nothing needs you" *or* "the run died on Tuesday".

| leg | what it is | catches | how fast |
|---|---|---|---|
| 1 | `run_completions` table — a row at start, updated at the end | a run that died; a stale gap; degraded coverage | next run |
| 2 | `OnFailure=vss-failure@%n.service` on every unit | non-zero exit, `TimeoutStartSec=`, broken venv | seconds |
| 3 | `vss-checkin.timer`, daily 09:30, **a separate timer** | a disabled/masked timer that starts nothing; a wiped database | ≤ 24 h |
| 4 | `ExecStartPost=-deploy/vss-ping-healthcheck.sh` → healthchecks.io | **a dead VPS**, a dead network, a user manager that never started | at the far end's grace |

Leg 1 records **priced** coverage, not row count — a night when every fetch
failed cannot record itself as complete. A `--ticker` run and a `--dry-run`
**do not reset the 72-hour clock**; a week of one-ticker runs must not read as
a week of healthy ones. Leg 2 is `/bin/sh` + `curl` with no venv and no
package, because the failure being reported may *be* the Python. Leg 4
inverts the signal: the ping means "the run succeeded", and the alarm is the
ping's **absence**, which is the one alarm a powered-off box can still raise.

**Still not covered, and say so rather than implying otherwise:** the weekly
screen has no ping of its own (leg 1's 10-day bar and leg 3 cover it); a box
that is up and pinging but *wrong* (legs 1 and 3 carry coverage); and
healthchecks.io itself being down.

Detail: `reports/DEADMAN-2026-08-31.md`, `deploy/README.md`.
Tests: `tests/test_heartbeat.py`, 35 cases. The `OnFailure=` path was fired
deliberately on the VPS and observed in the journal.

### The comparison basis — made general

E93's provenance clause was written as a one-off and is not one. The rule it
was an instance of: **two rankings are only diffed when both were struck the
same way.** `screenwatch.basis_mismatches` is that rule, and its list is meant
to grow. Today: `provenance` (was it a real scheduled run?) and **`tiers`**
(was it the same universe?), the latter a new column on `screen_rankings`.

A mismatch on any field **withholds the pointer and never the report** — the
changes are still computed and printed. It stops applying by itself once two
consecutive runs agree. **Nothing expires on a date and nobody has to remember
anything**, which was the point of the ruling.

### Nothing was written that should not have been

No watchlist write, no PIPELINE entry, no growth view, and **the widened
ranking was deliberately not persisted to `screen_rankings`** — a hand run's
tier-A+B ranking would have poisoned E93's baseline.

## 2. WHAT WAITS ON YOU

**One thing, and it takes two minutes.**

### ☐ Create the healthchecks.io check and put its URL in the env file

Leg 4 is built, installed and tested, and it is **doing nothing** until the
URL exists. `HEALTHCHECK_URL` is unset, so the ping is silent (E92), which
means the one leg that covers a dead VPS is not yet covering it.

```sh
# 1. create a check at healthchecks.io — period 1 day, grace 6 hours
# 2. put its ping URL in the env file (NOT in the repository):
$EDITOR ~/.config/vss/vss.env          # HEALTHCHECK_URL=https://hc-ping.com/<uuid>
# 3. confirm it once by hand; the check should go green:
set -a; . ~/.config/vss/vss.env; set +a
deploy/vss-ping-healthcheck.sh
```

Tonight's 22:30 run then pings on its own and every one after it.

`run_completions` was empty until tonight, so **the 09:30 check-in and the
22:30 run will each say "no completed nightly run is on record"**. That is the
switch reporting honestly that it has nothing to compare to. It stops after
tonight's run completes.
